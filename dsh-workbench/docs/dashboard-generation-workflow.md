# 通用数据看板生成工作流（旧受控模式）

> 当前默认模式已切换为“原生 DSH 自由生成”：模型仅依据用户目标与 CSV 生成完整 HTML 并保存为 Revision；不再加载预置通用模板，也不要求模板 ID、Plan、确认或 Spec。本文件保留的是按需启用的旧受控模式说明。

> 原则：大模型负责理解、归纳、提出方案和解释；确定性系统负责计算、渲染、校验、保存与发布。
>
> 因此，模型不直接输出最终看板 HTML，也不自行决定未经确认的指标口径、数据值或视觉实现。

## 1. 为什么不直接由大模型生成看板

直接生成页面通常会混淆四类职责：

| 风险 | 直接生成的问题 | 工作流中的解决方式 |
| --- | --- | --- |
| 业务语义不确定 | 模型猜测指标定义、目标或比较基准 | 指标合同、语义检索、用户确认 |
| 数据不可信 | 模型无法保证粒度、单位、时间范围一致 | 数据画像、对账、质量与治理门禁 |
| 页面不可控 | 代码、图表、交互和样式难以稳定复用 | 视觉合同 + 模板渲染器 |
| 难以审计与迭代 | 无法追溯每个结论、公式与版本 | Plan、Spec、Manifest、Revision 生命周期 |

模型适合生成一个**可审核的看板方案**；系统根据已确认的方案，使用受控组件和公式构建看板。

## 2. 端到端工作流

```text
用户问题 / 数据资产 / 参考看板
        ↓
01. 看板 Brief：明确目的、受众、场景和成功标准
        ↓
02. 数据画像：字段、类型、粒度、范围、质量风险
        ↓
03. 语义验证：指标定义、数据资产、血缘和冲突检查
        ↓
04. DashboardPlan：字段映射、候选 KPI、图表、故事线、风险
        ↓
05. 人工确认：业务目标、口径、映射、图表和默认筛选
        ↓
06. DashboardSpec：不可变、可构建的已确认规格
        ↓
07. 确定性构建：模板、组件、计算、交互、视觉 token
        ↓
08. 自动校验：数据、指标、可视化、导出、隐私与治理
        ↓
09. Draft → Preview → Release：预览审阅、发布、版本回滚
        ↓
10. 使用反馈：将高频修改回写为模板、规则或指标字典
```

## 3. 各阶段输入、产物与责任边界

| 阶段 | 模型可做什么 | 系统必须做什么 | 产物 |
| --- | --- | --- | --- |
| 01 Brief | 提炼用户问题、识别待确认假设 | 保存显式需求与边界 | `DashboardBrief`（建议新增） |
| 02 数据画像 | 建议字段角色和候选粒度 | 读取数据、推断类型、计算质量统计 | `DatasetProfile` |
| 03 语义验证 | 生成检索问题、解释证据 | 检索元数据、读取详情、标记未解决冲突 | `SemanticContext` |
| 04 方案 | 提议指标、筛选、图表、故事线和风险 | 约束 JSON 结构、标注推断来源和置信度 | `DashboardPlan` |
| 05 确认 | 解释取舍、根据反馈修订方案 | 阻止未确认、缺证据或冲突方案进入构建 | `DashboardPlanConfirmation` |
| 06 规格 | 不再自由生成 | 冻结已确认字段、口径、图表和视觉合同 | `DashboardSpec` |
| 07 构建 | 不参与最终 HTML 自由拼接 | 使用模板和受控组件渲染、执行公式 | Dashboard Model / HTML |
| 08 校验 | 解释失败原因和修复建议 | 计算对账、规则校验、视觉/导出验证 | Validation Report |
| 09 发布 | 生成摘要与变更说明 | Revision、审批、权限、审计、回滚 | Draft / Preview / Release |

当前工作台已有 `DatasetProfile`、`SemanticContext`、`DashboardPlan`、`DashboardSpec` 和 Revision 生命周期；`DashboardBrief` 可先作为 Plan 的输入界面或文档层实现，无需立即改变渲染链路。

## 4. 通用看板 Brief 模板

任何看板生成前，先完成以下最小信息集；无法回答的项目应作为阻断问题，而不是由模型补全。

| 项目 | 必填内容 |
| --- | --- |
| 看板目的 | 用户要理解、监控、诊断、规划或展示什么？ |
| 目标受众 | 谁使用、以什么频率、在什么会议或工作节点使用？ |
| 主问题 | 看完后需要作出什么判断或行动？ |
| 看板类型 | 总览、监控、诊断、规划、探索、协同或对外展示 |
| 核心指标 | 3–5 个指标及目标/比较基准 |
| 关键维度 | 时间、组织、区域、对象、渠道、状态等 |
| 数据范围 | 来源、时间范围、数据粒度、刷新频率、已知限制 |
| 交付边界 | 下钻、明细、导出、订阅、权限、移动端、离线导出等 |
| 验收标准 | 用户如何判断看板已满足目标？ |

## 5. 方案生成规则

`DashboardPlan` 是模型唯一可直接生成的核心工件，必须满足以下规则：

1. 将**事实、推断和待确认问题**分开记录。
2. 每个指标必须包含来源字段、公式、聚合方式、格式、粒度和置信度。
3. 每个图表必须先声明它要回答的问题，再选择图表类型。
4. 筛选项只保留会显著改变结论的维度，并标注全局或局部作用域。
5. 默认信息架构必须保留：语境、结论、变化/结构、探索和数据可信度。
6. 缺失时间字段、单位冲突、粒度冲突、关键字段未映射或语义证据不完整时，必须阻断确认。
7. 视觉偏好只能转成受校验的 `DashboardVisualContract`，不得生成任意 CSS、外部脚本或不可审计资源。

## 6. 模板选择与渲染规则

模板由两部分组成：

```text
业务数据合同：字段角色、指标公式、风险/比较规则、默认故事线
视觉合同：布局、色板、字体、组件 token、响应式规则
```

模型只能选择或提出模板候选；确定性渲染器必须：

- 根据数据合同计算真实指标，而不是使用模型编造的数值；
- 根据视觉合同渲染受控图表与组件；
- 为每个结论保留到指标口径与明细数据的可追溯路径；
- 保留数据截止时间、来源、范围和已知限制；
- 在模板不匹配时返回缺口，不静默拼接一个“看起来合理”的页面。

### 已确认 Spec 优先于领域模板

领域模板（内容运营、财务、产销）只能用于**快速构建的默认建议**，不能覆盖用户已确认的看板意图。只要构建请求携带已确认的 `DashboardSpec`，工作台必须采用 Spec 驱动渲染：

- 页面标题取 `Spec.title`；KPI 取已确认的 `Spec.metrics`，而非领域模板的固定指标；
- 趋势、结构、明细区块取 `Spec.charts` 的标题、维度与指标；
- 数据计算只允许受控公式（如 `SUM`、`AVG`、`COUNT`、`DISTINCT_COUNT`、加权平均、Top-N 和比率），无法计算时显式标记缺口；
- 领域模板仍可提供字段候选、默认公式和风险提示，但不得把一个内容或财务看板渲染成“库存/DOS 看板”。

这使“通用”落在可审核的 Spec 上，而不是让模型自由生成不可复现的 HTML。对于需要专有计算、专有交互或行业图表的场景，再将已验证模式沉淀为新的领域模板。

## 7. 确认与治理门禁

构建前至少确认：

```text
业务目标
数据范围和粒度
字段映射
全部核心 KPI 的口径与比较基准
图表所回答的问题
默认筛选与下钻路径
视觉合同
```

以下情况必须阻断：

- 指标存在多种定义且尚未选择；
- 数据实际值、单位或粒度无法对账；
- 语义上下文为 `incomplete`；
- 缺少时间字段却要求趋势/同比；
- 看板声明了“预警/行动”但没有规则、责任或处理状态；
- 用户未确认模型提出的关键映射、指标或图表。

### 文件型看板的工具契约

模型不应手工拼接治理对象。对已确认的 `DashboardSpec`，调用 `workbench_assess_dashboard_governance` 时传入 `spec` 与原始 `csv`；工作台会生成并返回标准化的 `governance`。将该返回对象（或其中的 `governance` 字段）原样传入 `workbench_build_dashboard`。

确认 Plan 时必须传入两个 ID 数组，且只能确认 Plan 已有的指标和图表：

```json
{
  "businessConfirmed": true,
  "confirmedMetricIds": ["..."],
  "confirmedChartIds": ["..."]
}
```

若需新增 KPI、图表类型或数据计算，先确认它能由 Spec 驱动渲染器的受控公式与组件支持；不支持时再扩展领域模板和确定性渲染器，然后重新生成 Plan。确认步骤不能用来绕过计算与治理边界。

## 8. 发布后的反馈闭环

不要把每一次用户修改都当成一次性页面改动。按以下层级沉淀：

| 反馈类型 | 应回写的位置 |
| --- | --- |
| 指标定义错误或新增 | 指标字典、数据合同、语义资产 |
| 默认筛选/比较方式不合适 | `DashboardPlan` 规则或业务模板 |
| 视觉层级、图表样式问题 | 视觉合同或设计模板 |
| 同类数据反复需要相同页面 | 新的业务数据合同与受控模板 |
| 数据质量问题 | 数据接入、对账与治理规则 |

这样模型会逐步从“临时设计者”转为“基于已验证资产进行编排的助手”，而看板质量随模板、规则和指标字典积累稳定提升。

## 9. 与当前 DSH 工作台的对应关系

| 工作流阶段 | 当前模块/能力 |
| --- | --- |
| 数据画像 | `src/data-ingestion/csv-profile.ts` |

| 受控数据合同与信息架构 | `src/dashboard-build/universal-contract.ts` |
| 确定性构建 | `src/dashboard-agent/builder.ts`、`src/dashboard-build/*` |
| 治理、指标合同与对账 | `src/dashboard-policy/*` |

| Draft / Preview / Release | `src/library/*`、`src/local-app/*` |

下一步应优先补齐 Brief 的交互采集、模板选择解释、Plan 审阅界面和构建前门禁提示；不应优先扩展模型直接生成 HTML 的能力。
