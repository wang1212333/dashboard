DSH HARNESS · PRODUCT / ALGORITHM / ENGINEERING

从“AI 生成网页”到
“可协作、可同步的 AI 工作台”

以 DSH Harness 的插件化编排能力为底座，构建 HTML + 智能 Markdown + 智能 CSV 的轻应用平台。目标不是替代成熟业务系统，而是让个人与小团队在几分钟内获得可持续演进的工作台。

技术方案 v1.0适用对象：产品 / 算法 / 前后端 / 平台2026.08

01 / WHY

产品命题：让“生成的内容”成为“持续运转的资产”

当前 AI 生成 HTML 常停留在一次性输出：页面由浏览器 localStorage 保存，跨设备即失效；后续修改需要回到代码；协作、审阅、版本与发布彼此割裂。DSH 轻应用以统一资料库为事实源，把内容、交互与数据拆成可独立演进、又能相互引用的三个原子格式。

一句话目标：用户用自然语言或所见即所得方式创建并维护页面；页面的数据写入受控的智能 CSV；多人、AI、设备与发布链接始终读取同一份可追溯事实源。
MARKDOWN

内容与审阅层

承接需求、方案、说明与 AI 修订建议；人对每一项建议拥有最终接受权。

HTML

交互与呈现层

承接大屏、表单、看板、移动端体验和链接发布；支持选区定点修改与代码兜底。

CSV

数据与状态层

承接轻量结构化记录、视图筛选和聚合；在线同步，避免设备本地状态成为唯一副本。

02 / ARCH

总体架构：DSH Harness 负责“理解、编排、执行”，资料库负责“存储、协作、发布”

采用前端轻运行时 + 服务端应用网关 + 插件能力面三层结构。所有写操作经过应用网关，HTML 不直接持有数据库密钥；Harness 将自然语言请求拆解为可审计的工具调用。

架构图的重点是边界：浏览器负责体验，网关负责授权与数据写入，Harness 只通过受控工具访问能力，资料库保存可回滚资产。
03 / CORE

三条核心体验链路，统一为“意图 → 计划 → 可审阅变更 → 提交”

不让模型直接覆盖用户资产。Harness 产出的是结构化计划和 diff；用户、权限策略或自动化规则决定是否提交。

A. 页面编辑

选区修改与可视化编辑

  • 编辑模型为 HTML AST / 组件树，渲染节点注入稳定 data-dsh-id。
  • 选区序列化为 assetId + nodeId + range + intent。
  • HTML 工具只对目标 AST 子树生成 patch，并运行截图 / DOM 校验。
  • 文本节点可 WYSIWYG 编辑；复杂结构回到受控组件或源码模式。
B. 协作与审阅

人、AI、同事同一条版本线

  • 以 Yjs 结构化文档模型同步，不直接对浏览器真实 DOM 做 CRDT。
  • AI 修改永远标记为 suggestion，不直接写入正式版本。
  • 接受建议时生成原子提交；作者、来源、diff、模型任务均可追溯。
  • 软锁仅提示正在编辑区域；离线和并发合并仍由 CRDT 负责。
C. 轻应用

页面与数据双向绑定

  • HTML 通过受限 SDK 声明数据需求，而非读写 localStorage。
  • CSV 定义 schema、记录、视图与聚合；云端为主，本地离线队列为辅。
  • 写入成功后以 WebSocket 广播行级变更。
  • 页面迭代不覆盖 CSV，绑定关系由 schema contract 保持。
04 / DATA

智能 CSV：以“表格文件体验”承载在线、可校验、可同步的数据

CSV 是用户可理解、可导入导出的呈现格式；线上运行时不应把原始文本 CSV 当作并发数据库。建议采用“逻辑 CSV + 行级存储 + 版本快照”的双表示模型。

1. Schema 注册字段类型、默认值、校验、索引、权限
2. 行级写入客户端携带 mutationId 与 baseVersion
3. 服务端提交事务、幂等、冲突检测、审计事件
4. 实时分发订阅者获得增量 patch，刷新派生视图
5. 导出快照随时导出兼容 CSV，供人和 AI 再利用

建议的数据实体

// application manifest app: { id, workspaceId, entryAssetId, publishedRevision } binding: { componentId, tableId, query, writePolicy } table: { id, schemaVersion, columns[], rowVersion } row: { id, data, createdAt, updatedAt, version } revision: { assetId, parentId, diff, actor, source } audit: { traceId, action, resource, result, timestamp }

冲突与离线策略

  • 默认：字段级 last-write-wins + 版本向量记录，适合待办、打卡、记账等轻量记录。
  • 关键字段：使用 baseVersion 乐观锁；版本不一致返回 409，并在 UI 中展示“我的修改 / 最新值”。
  • 离线：IndexedDB 仅缓存最近快照与 mutation queue；恢复网络后按 mutationId 幂等重放。
  • 数据保护：删除为软删除，按工作空间策略保留 30–180 天；每个发布版本绑定可恢复快照。
关键取舍不承诺把 CSV 做成高并发 OLTP 数据库。单表建议控制在 10 万行以内、常用查询在已声明索引内；超过规模或涉及复杂事务时，通过 Connector 接入专业数据库 / SaaS。
05 / RELEASE

版本、迁移与发布：让“持续更新”不等于“线上内容被意外改掉”

吸收 WorkBuddy 方案中的操作日志、周期快照与在线发布思路，并将其拆为可审计的草稿、预览和正式版本，避免把编辑态直接暴露给访问者。

VERSION STRATEGY

操作日志 + 周期快照

  • 协作层保存压缩后的 CRDT 更新；业务层保存“人 / AI / 工具”可读 revision。
  • 满足 50 次有效操作、5 分钟、发布前或累计更新超过阈值时创建快照；阈值由文档大小动态调整。
  • 回退先定位快照，再重放更新；旧更新归档压缩，但 revision 摘要与审计链永久保留。
  • AI 建议、接受建议、人工编辑分别标注来源，便于比较与合规复盘。
MIGRATION

localStorage 平滑迁移

  • 首次接入先扫描键、数据量、JSON 可解析性与潜在敏感字段，生成迁移预检报告。
  • 将本地记录映射至目标 schema，补齐 recordId 与 migrationId；服务端用二者幂等去重。
  • 导入后比对记录数、失败行与校验摘要，提供“查看差异 / 重试 / 回滚”入口。
  • 不自动清空本地数据：先备份，保留恢复窗口，只有用户确认后才清理旧缓存。
Draft个人或团队编辑态；可多人协作
Preview生成隔离预览；跑绑定与安全检查
Release冻结 revision，构建静态资源并分发 CDN
Promote / Rollback显式切换线上版本；一分钟内可回退
发布约束正式链接默认指向不可变的 Release Revision；编辑草稿不会自动影响线上页面。只有开启“跟随最新正式发布”时，CDN 才在新 Release 产生后刷新。预览链接可启用 WebSocket 热更新，正式链接仅接收受控发布事件。

06 / PLUGIN

Harness 插件设计：将能力封装成可发现、可授权、可回滚的工具

遵循 DSH Harness 的核心原则：插件声明能力，不持久化跨租户状态；运行时由宿主负责上下文注入、工具路由、权限校验、任务审计与取消。

插件职责输入 / 输出写入保护
asset-editor读取 HTML / MD，定位选区，生成 AST / 文本 diffselection + intent → patch set只产出 patch；apply_revision 才能提交
data-workbench建表、查询、聚合、写行、导入导出schema / query / mutation → rows / receiptschema 校验、幂等键、行级 ACL、速率限制
app-runtime生成 manifest、绑定组件与数据源、预览验证asset + bindings → preview / diagnostics只允许声明白名单组件和 SDK API
collaboration创建建议、评论、审阅、版本比较与回滚diff / comment → revision event审批策略、保护分支、不可篡改审计
publisher预发布检查、生成不可变构建、分发链接revision → release URL扫描敏感信息、域名与可见性策略

插件清单（示意）

{ "name": "asset-editor.apply_patch", "description": "提交经过审阅的资产补丁", "inputSchema": { "assetId": "string", "baseRevision": "string", "patches": "Patch[]", "approval": "required" }, "scopes": ["asset:write"], "idempotency": "taskId" }

一次“给左上角加猫头像”的执行编排

  1. Planner 从当前页面、选区和用户意图生成 AppChangePlan。
  2. Router 调用 asset-editor.plan_patch，限制触及的节点集合。
  3. Agent Runtime 在隔离预览沙箱执行，比较 DOM、可访问性与数据绑定回归。
  4. 返回可读 diff、截图和风险提示；用户确认后调用 apply_patch。
  5. 资料库创建 Draft revision；仅在显式发布后生成 / 更新 Release 链接。
07 / TRUST

治理原则：把“能生成”与“能写入 / 能发布”分开

轻应用面对的主要风险不是模型回答错误，而是模型、协作者或嵌入脚本越权修改数据和公开内容。安全设计应落在每个强制执行面。

IDENTITY

身份与权限

工作空间、资源、行三级 RBAC；发布链接可选公开、组织内、指定成员、密码 / 过期。服务端签发短时 scope token，浏览器无永久写凭证。

GUARDRAIL

生成与运行隔离

HTML 运行在 CSP + iframe sandbox 中；SDK 仅开放声明式读写 API。禁止任意外链脚本、直接网络访问与 secret 注入。

TRACE

可回退、可解释

每次人机修改绑定 actor、taskId、工具输入摘要、diff、审批与结果。操作失败 / 拒绝也写入审计流，支持按 revision 恢复。

控制面必须实施的控制验收证据
编辑 / AI 工具工具白名单、最小 scope、建议态、内容与代码扫描越权工具调用被拒绝且有 traceId
数据 API工作空间隔离、行级 ACL、schema 校验、幂等与限流跨空间 rowId 访问返回 404 / 403
发布运行时CSP、沙箱、资源代理、敏感字段脱敏、访问日志页面无法从客户端提取写 token
版本与恢复不可变 revision、快照、软删除、审计保留任意发布版本可回到指定 revision
08 / PLAN

建议按风险递增交付：先让资产可维护，再让数据可持续

每阶段都产出可验证的用户价值，避免先构建“万能低代码平台”。

P0 · 资料库与版本基座（4–6 周）

HTML / Markdown 资产模型、revision、WYSIWYG + 源码编辑、发布链接、人工协作与回滚。

P1 · 受控 AI 修改（4 周）

选区锚定、Harness asset-editor 插件、建议态 diff、预览诊断、任务审计。

P2 · 智能 CSV 轻应用（6–8 周）

schema、行级 API、绑定 SDK、实时订阅、移动端写入、离线 mutation queue。

P3 · 生态与规模化（持续）

模板市场、Connector、自动化工作流、用量治理、企业 SSO / DLP / 专有部署。

首批上线门槛（Golden Cases）

  • 定点改页：对含图表的 HTML 选中一句话修改，DOM 仅变化目标节点，95% 任务可一次通过预览。
  • 多人协作：两人同时编辑同一页，3 秒内显示对方更新；任意一次提交可定位作者和 diff。
  • 跨端记录：手机新增“早餐记录”后，桌面端订阅页面 2 秒内更新；断网后恢复可幂等补写。
  • 持续演进：给已绑定数据的页面加视觉组件，原表、历史记录和发布链接均不丢失。
  • 安全回归：发布页不能直接访问非授权表；工具不能绕过审批执行破坏性写入。

P95 查询 < 500msP95 写入 < 800ms变更可追溯率 100%发布回滚 < 1 min

结论：DSH 的差异化不在于“又生成一个 HTML”，而在于把页面、数据、协作和 AI 工具调用放进同一条受控生命周期。HTML 是交互界面，Markdown 是可审阅的知识载体，CSV 是可同步的数据契约，Harness 则是把自然语言安全转换为可验证变更的执行层。
